## 3. Root-cause candidates (ranked)

### Candidate A — React Query refetch race (HIGH confidence — explains the repeat)

**What happens:**  
`handleTrackStoryletChoice` calls the resolve API (`POST /api/tracks/resolve`), then calls `queryClient.refetchQueries({ queryKey: ["daily-run", userId] })` (lines 1193/1206/1214 in `play/page.tsx`). The refetch is async. Between the moment the resolve call returns and the moment the refetch completes, there is a window where:

1. `resolvedTrackStoryletIds` has been updated client-side to include the just-resolved `storylet_key`
2. BUT React Query fires a background refetch of `getOrCreateDailyRun`
3. The server responds with the updated `trackStorylets` (storylet now in `resolved_storylet_keys`) — but if the refetch races the DB write, the server may return the OLD row where that storylet is not yet in `resolved_storylet_keys`
4. React state is briefly populated with server data that does NOT include the resolve, while `resolvedTrackStoryletIds` is the only client-side guard filtering it out

**Why `resolvedTrackStoryletIds` sometimes fails as a guard:**  
The display filter at line 3877 is:
```typescript
trackStorylets.filter((b) => !resolvedTrackStoryletIds.has(b.storylet_key))
```
This works IF `resolvedTrackStoryletIds` has been updated before the refetch completes. But `setResolvedTrackStoryletIds` is a React state setter — its update is asynchronous (batched). If the refetch resolves before React commits the state update, the filter runs against the OLD `resolvedTrackStoryletIds` and the storylet re-appears briefly.

**Why it's consistent across accounts:**  
Timing is deterministic in fast network/local dev sessions. A fast Supabase response on the refetch races reliably against React's async batching.

**Verifying probe:**  
Add a `console.log` before and after the refetch call, and a `console.log` inside the `resolvedTrackStoryletIds` display filter:
```typescript
// In handleTrackStoryletChoice, after setResolvedTrackStoryletIds:
console.log('[RACE-PROBE] resolvedIds updated:', [...newResolved]);
// In the refetch callback:
console.log('[RACE-PROBE] refetch complete, trackStorylets:', trackStorylets.map(b => b.storylet_key));
// In display filter:
console.log('[RACE-PROBE] filtering with resolvedIds:', [...resolvedTrackStoryletIds], 'against beat:', b.storylet_key);
```
If a resolved key appears in `trackStorylets` at refetch time but NOT in `resolvedTrackStoryletIds` at filter time, the race is confirmed.

**Alternative probe (no code change):** In browser DevTools Network tab, time the resolve POST vs. the subsequent `getOrCreateDailyRun` GET. If the GET returns within the same render cycle as the POST response, the race window is open.

### Candidate B — Line 2777 type mismatch: `markDailyComplete` never fires (HIGH confidence — different symptom, same root effect)

**What happens:**  
In `play/page.tsx` at line 2777:
```typescript
trackStorylets.every((b) => newResolved.has(b.progress_id))
```
`newResolved` is constructed as:
```typescript
const newResolved = new Set([...resolvedTrackStoryletIds, beat.storylet_key]);
```
This is a `Set<string>` of **storylet_key strings** (e.g., `"lunch_floor"`, `"evening_choice"`).

But `b.progress_id` is a **UUID** (e.g., `"3f8a1b2c-..."`).

A storylet_key string never equals a UUID. So `newResolved.has(b.progress_id)` is always `false`. The `.every()` call is always `false`. **`markDailyComplete` is never called through this code path.**

**Evidence in the same file:**  
The comment at lines 326-330 explicitly documents that `resolvedTrackStoryletIds` is keyed on `storylet_key`, not `progress_id`:
> "Stores the `storylet_key` of storylets the player has resolved this segment. NOT progress_id — one progress row (per-track) can surface multiple storylets across a day..."

All other uses of `resolvedTrackStoryletIds` correctly reference `storylet_key` (lines 540, 3877, 3907). Line 2777 is the sole exception.

**Effect on the repeat symptom:**  
`markDailyComplete` not firing means the current day is never marked complete through the track-storylet path. Downstream effects depend on what `markDailyComplete` gates:
- If it gates `daily_states` advancement, the current-day pool keeps being served
- If daily advancement proceeds via another path (routine-week server tick), this bug's effect on repeats may be partial or session-scoped

**Verifying probe:**  
```typescript
// Temporary log at line 2773, before the condition:
console.log('[DAILY-COMPLETE-PROBE] trackStorylets progress_ids:', trackStorylets.map(b => b.progress_id));
console.log('[DAILY-COMPLETE-PROBE] newResolved (storylet_keys):', [...newResolved]);
console.log('[DAILY-COMPLETE-PROBE] condition result:', trackStorylets.every((b) => newResolved.has(b.progress_id)));
```
Expected: condition always logs `false`. If it does, this is confirmed.

Alternative: check `daily_states` in the DB after resolving all track storylets on a given day. If `is_complete` remains `false`, `markDailyComplete` is not firing.

```sql
SELECT day_index, is_complete, updated_at
FROM daily_states
WHERE user_id = 'YOUR_USER_ID'
ORDER BY day_index DESC
LIMIT 5;
```

### Candidate C — `current_storylet_key` stale fallback (MEDIUM confidence — present in code, not currently triggered)

**What happens:**  
In `resolve/route.ts` lines 123-125, `effectiveStoryletKey` is resolved as:
```typescript
const effectiveStoryletKey = clientStoryletKey ?? next_key_override ?? current_storylet_key;
```
If the client sends no `storylet_key`, the engine falls back to `next_key_override` (correct for chain mode), then to `current_storylet_key` (last chain endpoint — potentially stale after a segment advance).

**Current state:**  
The resolve payload (lines 2565-2569 in `play/page.tsx`) always sends:
```typescript
storylet_key: beat.storylet_key,
progress_id: beat.progress_id,
```
So `clientStoryletKey` is always present in the current client. The fallback does not trigger today.

**Why it's on the list:**  
If a future client-side change drops `storylet_key` from the payload, or if an older client session (browser tab) submits a resolve from stale state, this path becomes live. At that point, the engine resolves the wrong storylet_key and the correct one remains unresolved.

**Verifying probe:**  
```sql
-- Compare what the client reports vs what the engine resolved
SELECT cl.storylet_key AS client_reported, tp.current_storylet_key AS engine_current
FROM choice_log cl
JOIN track_progress tp ON cl.user_id = tp.user_id
  AND cl.track_id = tp.track_id
WHERE cl.storylet_key != tp.current_storylet_key
  AND tp.updated_at > NOW() - INTERVAL '1 hour';
```
0 rows = not currently triggering. Non-zero = the fallback is firing unexpectedly.

### Candidate D — `hasFutureContent` strict `>` (LOW confidence — different symptom)

**What happens:**  
In `resolve/route.ts` lines 347-351:
```typescript
const hasFutureContent = storyletsOnTrack.some(
  (s) => (s.due_offset_days ?? 0) > currentDayOffset
);
```
The `>` is strict (not `>=`). A storylet with `due_offset_days === currentDayOffset` that hasn't been resolved yet is NOT counted as "future content." The engine may therefore mark a track as complete (no future content) prematurely, closing pool selection too early.

**Effect on repeats:**  
This is not a direct repeat vector — it causes premature track completion, not re-surfacing of resolved content. A track that closes early stops serving content; it doesn't re-serve old content.

**Why it's on the list:**  
If the premature close causes the track to be marked "done" and then re-initialized on the next `buildInitialTrackProgress` call (e.g., after a reset/reload), the initial storylet could re-appear at position 1.

**Verifying probe:**  
```sql
-- Find tracks with unresolved same-day storylets that hasFutureContent would miss
SELECT t.key, s.storylet_key, s.due_offset_days, tp.current_day_offset
FROM track_progress tp
JOIN tracks t ON tp.track_id = t.id
JOIN storylets s ON s.track_id = t.id
WHERE tp.user_id = 'YOUR_USER_ID'
  AND s.due_offset_days = tp.current_day_offset  -- same day
  AND s.is_active = true
  AND NOT (s.storylet_key = ANY(tp.resolved_storylet_keys));
-- Any row here is a storylet hasFutureContent strict-gt would mis-classify as "no future content"
```

## 4. Regression gate (playthrough script)

This script verifies that resolving `lunch_floor` removes it from the served pool and prevents re-surfacing. Run it against a fresh user session after any fix lands.

```sql
-- SETUP: Get user_id for the test account
SELECT id AS user_id FROM auth.users WHERE email = 'YOUR_TEST_EMAIL';

-- STEP 1: Confirm lunch_floor is in the belonging track and served on day 0
SELECT s.storylet_key, s.due_offset_days, s.expires_after_days, s.segment, s.default_next_key
FROM storylets s
JOIN tracks t ON s.track_id = t.id
WHERE t.key = 'belonging' AND s.storylet_key = 'lunch_floor';

-- STEP 2: Before resolve — confirm lunch_floor is NOT in resolved_storylet_keys
SELECT resolved_storylet_keys
FROM track_progress
WHERE user_id = 'YOUR_USER_ID'
  AND track_id = (SELECT id FROM tracks WHERE key = 'belonging');
-- Expected: lunch_floor NOT present in the array

-- STEP 3: After the player resolves lunch_floor in the browser (or via API call):
-- Trigger the resolve via the game UI, then run:
SELECT resolved_storylet_keys
FROM track_progress
WHERE user_id = 'YOUR_USER_ID'
  AND track_id = (SELECT id FROM tracks WHERE key = 'belonging');
-- Expected: lunch_floor IS present in the array

-- STEP 4: Pool scan — confirm lunch_floor is filtered from the next engine call
-- (mirrors selectTrackStorylets.ts pool logic)
SELECT s.storylet_key, s.due_offset_days, s.segment
FROM storylets s
JOIN tracks t ON s.track_id = t.id
JOIN track_progress tp ON tp.track_id = t.id AND tp.user_id = 'YOUR_USER_ID'
WHERE t.key = 'belonging'
  AND s.is_active = true
  AND s.due_offset_days <= tp.current_day_offset
  AND (
    tp.current_day_offset <= s.due_offset_days + s.expires_after_days
  )
  AND NOT (s.storylet_key = ANY(tp.resolved_storylet_keys));
-- Expected: lunch_floor NOT in result set

-- STEP 5: daily_states completion check
SELECT day_index, is_complete, updated_at
FROM daily_states
WHERE user_id = 'YOUR_USER_ID'
ORDER BY day_index DESC
LIMIT 3;
-- Expected: the day containing lunch_floor is marked is_complete = true
-- If is_complete = false after all track storylets resolved, Candidate B is confirmed

-- STEP 6: choice_log dedup — confirm no double-entry
SELECT storylet_key, count(*) AS resolve_count
FROM choice_log
WHERE user_id = 'YOUR_USER_ID' AND storylet_key = 'lunch_floor'
GROUP BY storylet_key;
-- Expected: exactly 1 row with resolve_count = 1
```
